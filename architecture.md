# Архитектура сервиса голосований

Документ описывает архитектуру, нагрузочный расчёт и обоснование выбранных решений.
Инструкции по запуску и тестированию — в [README.md](./README.md).

---

## 1. Что определяет архитектуру

Задача выглядит как простой CRUD: создать опрос, принять голос, показать результаты.
Доменная модель тривиальна и умещается в три таблицы. Вся сложность — в одном свойстве
нагрузочного профиля:

> ~100 млн зрителей получают призыв к действию одновременно и голосуют в течение ~60 секунд.

Из этого следуют три ограничения, которые определяют каждое решение ниже.

**Нагрузка не средняя, а импульсная.** Система 99,99% времени простаивает и обязана
выдержать один всплеск. Оптимизировать пропускную способность в среднем бессмысленно —
значение имеет только поведение в пике.

**Реагировать во время события невозможно.** Шестьдесят секунд — это меньше, чем время
срабатывания алерта, меньше, чем цикл автоскейлинга, и несопоставимо со временем реакции
человека. Оператор не успеет ничего: ни добавить мощности, ни переключить трафик, ни
принять решение. Поэтому **все деградации предопределены заранее и зашиты в код**
(fail-open, grace period, circuit breaker), а не управляются в момент инцидента. Система
должна выйти на пик уже прогретой и готовой.

**Цена ошибки — весь эфир.** Второго прогона не будет: ролик уже показан, зрители уже
ушли. Отказ на 20-й секунде уничтожает результат целиком, а не портит его частично.

Дополнительно ТЗ фиксирует, что дедупликация **намеренно слабая** — «достаточная на
уровне обычных, не технически подкованных пользователей». Это не упрощение ради сроков,
а требование: строгая идентификация противоречит анонимности и отсутствию регистрации.

## 2. Нагрузочный расчёт по слоям

### Исходные допущения

| Параметр | Значение | Обоснование |
|---|---|---|
| Зрителей | 100 млн | из ТЗ |
| Явка | 10% → 10 млн голосов | консервативная оценка для ТВ-голосования |
| Окно | 60 с | из ТЗ |
| Распределение | ~50% голосов в первые 20 с | всплеск сразу после появления QR, затем хвост |
| **Средний RPS** | **167 000** | 10 млн / 60 с |
| **Пиковый RPS** | **~250 000** | 5 млн / 20 с |

Проектируем на 300K RPS, чтобы явка вдвое выше ожидаемой не потребовала изменений.

### Сколько доходит до каждого слоя

```
100 000 000 открытий лендинга
        │
        ▼
   ┌─────────┐
   │   CDN   │  статика лендинга, кэш-хит ~100%
   └────┬────┘  → до origin доходит ~0
        │
        ▼
   ┌─────────────────┐
   │ POST /api/token │  ~20 млн запросов, пик ~300K RPS
   └────┬────────────┘  чистый HMAC: без Redis, без Postgres
        │                (в roadmap уезжает на edge compute → origin не видит и их)
        ▼
   ┌─────────┐
   │  nginx  │  TLS, rate limiting по IP, load balancing
   └────┬────┘  срезает скриптовую накрутку до приложения
        │
        ▼  ~250 000 RPS
   ┌──────────────────────────────┐
   │  N × stateless Go-инстансов  │  ~15K RPS на инстанс → 20-24 инстанса
   └────┬─────────────────────┬───┘
        │                     │
        │ 250 000 ops/sec     │ батч раз в 150 мс
        ▼                     ▼
   ┌──────────┐        ┌──────────────┐
   │  Redis   │        │    Redis     │  ~1 000 ops/sec
   │  дедуп   │        │  счётчики    │  (24 инстанса × 6.7 flush/с × ~6 команд)
   └──────────┘        └──────┬───────┘
   ← узкое место               │ снапшот раз в 5 с
                               ▼
                        ┌────────────┐
                        │ PostgreSQL │  ~0.2 транзакции/сек
                        └────────────┘
```

Каждый слой дешевле следующего на порядки: 250K → 1K → 0.2. Это не побочный эффект,
а цель архитектуры — сводить импульс к постоянной нагрузке как можно раньше.

### Где реально кончается запас

**Дедупликация — единственный настоящий потолок.** Проверка «этот токен уже голосовал?»
не батчится и не откладывается: ответ нужен до того, как система примет голос. Это
250 000 синхронных round-trip'ов в секунду. Одна нода Redis — порядка 100K ops/sec,
значит нужен кластер минимум из 3 нод, на практике 4-6 с запасом.

Хорошая новость: **дедуп-ключи шардируются сами.** Токен уникален у каждого зрителя,
хеш равномерно распределён по слотам, никакой ручной схемы шардирования не требуется —
нужны просто ноды.

**Счётчики узким местом не являются**, вопреки интуиции. После батчинга на них приходится
~1000 ops/sec — меньше, чем на дедуп, в 250 раз. Шардирование счётчиков в схеме
присутствует, но это дешёвая страховка на случай роста явки, а не решение существующей
проблемы. Важно не перепутать: интуиция подсказывает бояться hot key на счётчике, а
реальный дефицит — в дедупе.

**Память Redis под дедуп** определяет размер кластера не слабее, чем throughput:

| Явка | Ключей | Память (~100 Б на ключ с TTL и накладными) |
|---|---|---|
| 10% | 10 млн | ~1 ГБ |
| 50% | 50 млн | ~5 ГБ |
| 100% | 100 млн | ~10 ГБ |

TTL ключей — до `ends_at` плюс запас, после чего память освобождается сама.

**PostgreSQL не участвует в горячем пути вообще.** 0.2 транзакции в секунду — нагрузка,
которой нет. Это осознанно: реляционная БД здесь нужна для админки и долговременного
хранения агрегатов, а не для приёма голосов.

## 3. Общая схема

### Путь голоса (hot path)

```
Зритель → QR / короткая ссылка
    │
    ├─→ GET /p/{id}          статика лендинга, CDN, без Set-Cookie
    └─→ POST /api/token      HMAC-токен → Set-Cookie (некэшируемо by design, см. §5.1)
    │
    ▼
POST /api/polls/{id}/vote
    │
   nginx: rate limit по IP → 429
    │
   Go-инстанс (любой, без sticky sessions):
    │
    1. now() >= ends_at + grace      → 410   in-memory, 0 RTT
    2. валидация option_ids           → 400   in-memory
    3. SET NX EX dedup:{poll}:{token} → 409   единственный RTT, таймаут 50 мс
    4. counters[i].Add(1); voters.Add(1)      in-memory, без блокировок
    5. 200 {"accepted": true}
                │
                │  flush раз в 150 мс
                ▼
        Redis: HINCRBY счётчиков + INCR voters (один пайплайн)
                │
                │  снапшот раз в 5 с, идемпотентный upsert
                ▼
        PostgreSQL: агрегаты
```

Порядок проверок — от бесплатных к дорогим. Сверка `ends_at` и валидация опций читают
процессную память и не стоят ничего; запрос к Redis идёт последним, только когда голос
уже признан валидным. После окончания ролика прилетает много запросов к закрытому опросу
(зрители досматривают запись, дожимают кнопку) — они отсекаются, не тронув Redis.

### Путь результатов (read path)

Промежуточные результаты во время голосования **не показываются** (см. §5.2). После
закрытия опроса ответ одинаков для всех, поэтому целиком уезжает в CDN:

```
опрос идёт              → 425 Too Early, Cache-Control: no-store
ends_at .. +N секунд    → max-age=5, stale-while-revalidate=30    (досходятся батчи)
после финального flush  → max-age=3600, immutable                 (число окончательное)
```

`stale-while-revalidate` и коалессинг запросов на edge (`proxy_cache_lock`) обязательны:
без них TTL истекает синхронно на всех edge-нодах и origin получает залп раз в 5 секунд.

Вторая фаза живёт считанные секунды, пока долетают последние батчи. Дальше результат
неизменяем и кэшируется как статика — именно тогда, когда приходит основная волна
читателей.

### Админка (cold path)

Обычный CRUD поверх PostgreSQL: создание опроса, список, просмотр агрегатов. Нагрузка
пренебрежимо мала, никаких специальных решений не требует. Админский эндпоинт результатов
работает и во время голосования, без кэширования.

## 4. Выбор технологий

### Go

- **Дешёвая конкурентность.** 250K одновременных соединений — это горутины по несколько
  килобайт, а не потоки ОС. Модель «горутина на запрос» остаётся применимой в пике.
- **Нет прогрева.** Инстанс, поднявшийся в середине эфира, работает на полной скорости
  сразу. У JVM тот же код первые секунды исполняется интерпретатором — а секунды здесь
  составляют заметную долю всего окна.
- **Предсказуемый хвост латентности.** Паузы GC — доли миллисекунды, что важно, когда
  вся система живёт минуту и p99 определяет долю потерянных голосов.
- **Статический бинарь.** Образ в десятки мегабайт, холодный старт — доли секунды.
- **Примитивы под задачу в stdlib:** `sync/atomic` для счётчиков, `context` для таймаутов,
  `singleflight` для защиты от stampede.

Альтернативы и почему нет: **Node** — один event loop на процесс, потолок на ядро ниже,
CPU-bound участки блокируют всё; **Python** — тот же аргумент, усиленный GIL и стоимостью
интерпретации; **Java** — Loom снимает проблему блокирующего I/O, но остаются прогрев JIT,
тяжёлый образ и медленный старт, то есть ровно те свойства, которые противопоказаны
системе без права на реакцию.

### Redis

Redis владеет **координационными инвариантами**, а не доменными данными:

- уникальность голоса (`SET NX` — атомарная проверка-и-установка без блокировок, за счёт
  однопоточности шарда);
- общий счётчик, к которому пишут все инстансы.

Ни один из этих объектов не переживает опрос: у дедуп-ключей TTL, счётчики после закрытия
переносятся в PostgreSQL. Потеря Redis не означает потерю данных — только деградацию
(см. §6). Это принципиально: Redis здесь не база, а точка синхронизации.

Встроенный TTL снимает необходимость в отдельной уборке 10 млн ключей.

### PostgreSQL

Долговременное хранилище опросов и агрегатов. Выбран по скучным причинам: ACID для
админского CRUD, честные ограничения целостности, `ON CONFLICT` для идемпотентного
upsert'а. Нагрузка на него настолько мала, что любая альтернатива обсуждалась бы
исключительно из вкусовых соображений.

### nginx

TLS-терминация, балансировка, rate limiting. Ограничение частоты вынесено сюда
сознательно — см. §5.3.

## 5. Ключевые решения

### 5.1. Токен выдаётся отдельным POST-эндпоинтом

**Проблема.** Токен — это cookie, то есть уникальное значение на зрителя. Если ставить
его заголовком `Set-Cookie` при отдаче лендинга, а лендинг кэшируется на CDN, то один
закэшированный ответ уедет **всем зрителям сразу**: все получат один и тот же токен,
первый `SET NX` выиграет, остальные 10 млн получат 409. Механизм защиты уничтожит опрос
полностью.

Большинство CDN по умолчанию отказываются кэшировать ответ с `Set-Cookie`. Опасность в
том, что дефолт перестаёт спасать при явном override вида «cache everything» — а это
ровно то, что включают, готовя лендинг к 100 млн зрителей. Триггером ошибки становится
сама оптимизация под нагрузку.

**Решение.** Не полагаться на заголовок, а разнести кэшируемое и некэшируемое по разным
URL и методам:

```
GET  /p/{id}       статика лендинга, без Set-Cookie, кэшируется агрессивно
POST /api/token    минт токена — POST не кэшируется ни одним CDN в принципе
```

`POST` не кэшируется по спецификации HTTP, а не по настройке. Ошибка становится
невыразимой: нет заголовка, который бы её включил, и нет page rule, который бы её создал.
Защита переносится из конфигурации в структуру.

**Что даёт подпись.** Токен — HMAC от `(poll_id, случайное значение, timestamp)`. Подпись
**не** защищает от массовой генерации: скрипт дёрнет эндпоинт 10 000 раз и получит
10 000 валидных токенов. Она защищает от **оффлайновой** генерации — без неё атакующему
хватило бы `uuid4()` в цикле, вообще без сети. HMAC превращает бесплатную атаку в атаку,
требующую сетевого запроса на каждый токен, то есть проходящую через rate limit. Это
ровно тот уровень, который просит ТЗ, и ни на грамм больше.

Эндпоинт — самый дешёвый в системе: чистый CPU, ноль обращений к хранилищам. Он же первым
переезжает на edge compute, когда оно появится.

### 5.2. Промежуточные результаты не показываются

Технически ничто не мешает возвращать агрегат прямо в ответе на голос: каждый инстанс
раз в секунду делает `HGETALL` по шардам и держит снапшот в памяти, так что отдача цифр
не стоит ни одного дополнительного round-trip'а.

Мы этого не делаем **по методологическим причинам**. Показ лидирующего варианта во время
голосования создаёт bandwagon effect: зритель видит, что вариант A ведёт, и голосует за A.
Для развлекательного голосования это допустимо, для национальной компании по проведению
опросов — дефект, обесценивающий сам продукт.

Побочная выгода: read path становится полностью кэшируемым (§3), потому что после закрытия
ответ одинаков для всех. Но основание — методология, а не экономия.

Механизм снапшота при этом реализован: он нужен админке и является читающим зеркалом
батчера — батч на запись, батч на чтение, и Redis не видит ни 250K записей, ни 250K чтений.

### 5.3. Cookie — дедуп, IP — только rate limit

**IP не годится для дедупликации.** За одним публичным адресом мобильного оператора
(CGNAT) сидят десятки тысяч абонентов. Правило «один голос с IP» при 100 млн зрителей
вырежет легитимное большинство — причём непропорционально: мобильных зрителей сильнее,
чем домашних.

Разделение ролей:

- **cookie-токен** — точный дедуп, `SET NX EX` на голос;
- **IP** — rate limiting со щедрым порогом (десятки запросов в минуту): ловит скрипт с
  одной машины, не задевает NAT.

**Rate limit живёт на nginx, а не в Redis.** Раз дедуп — потолок системы, тратить на
приблизительную проверку ещё 250K ops/sec в том же Redis нельзя. На nginx лимит становится
per-node вместо глобального: при K нодах фактический порог в K раз выше номинального. Для
порога такого масштаба это несущественно — он отсекает автоматизированную накрутку, а не
считает точный бюджет. Побочно исчезает классическая гонка `INCR`/`EXPIRE`.

В итоге на горячем пути остаётся **ровно один синхронный round-trip**, и это тот, который
несократим.

Обход дедупа очисткой cookie или переходом в режим инкогнито — ожидаемое поведение, прямо
разрешённое ТЗ.

### 5.4. Дедуп до инкремента

`SET NX` выполняется **до** увеличения счётчика. Обратный порядок допускал бы двойной
счёт при ретраях, что для опроса хуже.

Следствие нужно назвать честно: если инстанс жёстко умрёт с незасброшенным батчем, токен
уже сожжён, а голос до Redis не долетел — при повторной попытке зритель получит 409 и
проголосовать не сможет вообще. Это не «потеря единиц», а потеря права голоса.

Масштаб: батч теряет **один** инстанс, а не кластер. При 250K RPS и 24 инстансах отказ
одного стоит `250000/24 × 0,15 ≈ 1600` пользователей из десяти миллионов — 0,016%.
Плановый рестарт стоит нуля: graceful shutdown делает финальный flush. Число относится
только к жёсткому отказу ноды.

### 5.5. `ends_at` — данные, а не событие

Время окончания хранится в опросе; каждый инстанс сверяется с ним сам. Нет рассылки
«закрываемся», нет расхождения между подами, свежеподнятый инстанс работает корректно
сразу.

**Grace period.** Окно длится 60 секунд, и голос, отправленный на 59,8-й секунде, доедет
до бэкенда после дедлайна. Без запаса в 2-3 секунды режется хвост легитимных голосов,
причём тем сильнее, чем хуже у зрителя связь. Отсечка — по времени приёма, не по времени
обработки.

Grace period применяется **только к приёму**. Клиенту `ends_at` отдаётся без него, иначе
клиентский таймер и серверная отсечка разойдутся и появятся жалобы «кнопка активна, но
голос не принят».

**Клиентский таймер считается по offset'у, а не по часам устройства.** В ответе с
метаданными опроса возвращается серверное время; клиент вычисляет смещение и ведёт отсчёт
от него. Часы потребительских телефонов врут на минуты — без этого у части зрителей кнопка
погаснет на десятой секунде ролика. Расхождение NTP между серверами при этом составляет
десятки миллисекунд и полностью покрывается grace period.

### 5.6. Счётчики — массив atomic, без каналов

Число вариантов ответа мало (2-10) и известно на старте, поэтому счётчик — массив:

```go
type counter struct {
    v atomic.Int64
    _ [56]byte // паддинг до кэш-линии
}
```

Хендлер делает `counters[i].v.Add(1)` — без блокировок и без канала. Канал здесь был бы
точкой сериализации: все горутины упирались бы в одного читателя. Паддинг до 64 байт
обязателен — при 2-10 счётчиках подряд все они лягут в одну-две кэш-линии, и ядра будут
гонять их между собой (false sharing), теряя больше, чем стоила бы блокировка.

Flush-горутина по тикеру (150 мс) делает `Swap(0)` по каждому счётчику и отправляет один
пайплайн в Redis.

**Порога на размер батча нет, и это исправление к первоначальной спецификации.** Там он
обосновывался тем, что «иначе на пике батч успевает распухнуть за интервал». Для агрегации
счётчиков это неверно: за 150 мс уходит одинаковое число команд и при 10 RPS, и при 250 000 —
растёт только значение дельты, а `HINCRBY` от величины аргумента не дорожает. Батч здесь не
список событий, а фиксированный набор счётчиков. Порог не давал бы ничего, зато требовал бы
общего счётчика записей — то есть одной горячей кэш-линии на весь инстанс, ровно того, чего
избегает паддинг двумя абзацами выше.

**Важная деталь:** `Swap(0)` уже забрал значения из памяти. Если пайплайн упал, значения
возвращаются обратно через `Add(n)` и повторяются на следующем тике — иначе они теряются
при полностью живом инстансе.

При SIGTERM — финальный flush перед выходом.

### 5.7. Идемпотентный upsert снимает необходимость в лидере

Снапшот в PostgreSQL пишется абсолютным значением счётчика, а не дельтой, поэтому
повторная запись безопасна:

```sql
INSERT INTO poll_results (poll_id, option_id, votes, generation)
VALUES (...)
ON CONFLICT (poll_id, option_id) DO UPDATE SET
  votes = CASE
    WHEN EXCLUDED.generation > poll_results.generation THEN EXCLUDED.votes
    ELSE GREATEST(poll_results.votes, EXCLUDED.votes)
  END,
  generation = GREATEST(poll_results.generation, EXCLUDED.generation),
  updated_at = now();
```

Благодаря этому **любой инстанс может писать снапшот** — выборы лидера, распределённые
блокировки и выделенный воркер не нужны. Два инстанса с разной свежестью данных не
откатят счётчик назад.

`GREATEST` защищает от отката, но делает счётчик принципиально неспособным уменьшаться.
Отсюда колонка `generation`: монотонный номер прогона. При большей генерации значение
перезаписывается безусловно.

Это не отладочный костыль. Тот же механизм — единственный корректный способ пережить
потерю Redis в середине опроса: счётчики обнулились, отсчёт пошёл заново, и без генерации
`GREATEST` навсегда заморозил бы в PostgreSQL докризисные цифры. Заодно он даёт чистый
перезапуск локального стенда: без него поднятый с нуля Redis оставил бы в базе старые
числа, и это выглядело бы как баг.

### 5.8. Отдельный счётчик проголосовавших

При `kind = multiple` один запрос увеличивает несколько счётчиков, поэтому `sum(votes)`
перестаёт быть числом проголосовавших, и проценты, посчитанные от суммы, дадут больше
100%.

Счётчик участников инкрементируется один раз на запрос и хранится **отдельным ключом**
(`poll:{id}:voters:{shard}`), а не полем в хеше счётчиков. Поле в общем хеше заставляло бы
каждого читателя помнить про фильтрацию, и один забытый цикл по `HGETALL` показал бы в
админке фантомный вариант ответа — ошибку, которую невозможно поймать тестом на корректном
опросе.

Для `kind = single` число участников совпадает с суммой голосов. Этот инвариант проверяется
тестом: он бесплатно ловит ошибки в батчере.

## 6. Поведение при отказах

Шестьдесят секунд означают, что реакция невозможна. Поэтому каждый отказ имеет заранее
определённое поведение.

### Redis недоступен или деградировал → fail-open

- **fail-closed** (отдавать 503): опрос уничтожен полностью, национальный эфир прошёл
  впустую.
- **fail-open** (пропустить голос без дедупа, счётчик увеличить): теряется защита от
  накрутки на время инцидента, результат сохраняется.

Выбран fail-open. ТЗ прямо говорит, что дедуп слабый и обходится вручную — значит его
ценность заведомо ниже ценности самого результата.

**Реализация — таймаут и circuit breaker вместе, это разные слои:**

- **бюджет 50 мс на запрос** ограничивает урон от одного обращения. Нужен всегда: без
  него медленный Redis держит хендлер и зритель смотрит на спиннер.
- **circuit breaker по доле ошибок** ограничивает урон системный. Только бюджета
  недостаточно: если Redis жив, но отвечает за 200 мс, каждый запрос честно выждет свои
  50 мс, и при 250K RPS это мгновенно выест пул соединений и займёт все хендлеры. Breaker
  размыкает цепь после серии ошибок в скользящем окне, и последующие запросы идут мимо
  Redis **вообще без попытки**, с probe раз в несколько секунд. Деградация стоит первых
  нескольких десятков запросов, а не всего пика.

Состояние breaker'а **локальное для инстанса**. Распределённый breaker требовал бы
обращения к Redis, чтобы решить, стоит ли обращаться к Redis. За 60 секунд каждый инстанс
независимо придёт к тому же выводу за первые десятки запросов.

#### Бюджет соблюдается сторожем, а не таймаутом клиента

Первая версия этого раздела считала, что бюджет обеспечивается `context.WithTimeout`
вокруг вызова Redis. Измерения на стенде это опровергли, и разница принципиальная.

| Что проверяли | Худший запрос при бюджете 50 мс |
|---|---|
| `context.WithTimeout` вокруг вызова клиента | **16,7 с** |
| плюс `DialTimeout`/`ReadTimeout`/`PoolTimeout`, `MaxRetries: -1`, свой dialer | **10 с** |
| плюс сторожевой таймер в чекере | **54,7 мс** |

Диагностика развела два сценария отказа. Когда Redis не отвечает, но имя резолвится
(`docker compose pause`), бюджет соблюдался и без сторожа — 53 мс. Когда имя исчезает
(`docker compose stop`), запросы висели до 10 секунд: задержка не в дозвоне, а в ожидании
внутри клиента, и переданный контекст его не связывал.

Отсюда правило, которое стоит запомнить шире, чем этот проект: **контекст ограничивает
вызов только настолько, насколько библиотека этого хочет.** Там, где нужна гарантия, её
приходится держать самому — вызов уходит в горутину, вызывающий ждёт на `select` по
`ctx.Done()`. Цена — горутина и канал на голос, сотни наносекунд против миллисекундного
round-trip'а.

Почему без этого нельзя было обойтись: breaker по построению срабатывает **после** порога
ошибок, то есть первую партию запросов он не защищает вообще. Именно она и висела бы по
десять секунд — ровно тот выеденный пул, ради которого breaker вводился.

### Инстанс умер жёстко

Теряется его незасброшенный батч — ~1600 голосов из 10 млн (§5.4). Остальные инстансы
не затронуты: они не координируются между собой.

### Redis потерял данные в середине опроса

Счётчики начинают отсчёт с нуля. Восстановление — через инкремент `generation`, после
чего upsert перезаписывает агрегаты безусловно (§5.7). Дедуп-ключи теряются, что означает
временное fail-open по накрутке.

### PostgreSQL недоступен

На приём голосов не влияет вообще: горячий путь его не касается. Снапшоты копятся в Redis
и доедут при восстановлении. Недоступна только админка.

### Инстанс поднялся в середине опроса

Метаданные опроса подтягиваются им самостоятельно. Защита от stampede — `singleflight`
плюс процессный кэш: максимум один запрос на инстанс на опрос, то есть 100 одновременно
стартующих подов дают 100 запросов за одну строку, а не шторм.

### Прогрев (обязателен до эфира)

- Пулы соединений к Redis и PostgreSQL создаются и прогреваются при старте, а не лениво
  по первому запросу. Иначе первые секунды пика уйдут на установку сотен TCP-соединений.
- Опрос имеет состояние `armed` до `starts_at`: инстансы загружают метаданные в память
  **до** эфира, а не в первую секунду.
- Масштабирование — по расписанию эфира, а не реактивное по метрикам: автоскейлер не
  успеет.

## 7. Модель данных

### PostgreSQL

```sql
polls (
  id           uuid primary key,
  question     text not null,
  kind         text not null check (kind in ('single','multiple')),
  max_choices  int,                    -- только для multiple
  starts_at    timestamptz not null,
  ends_at      timestamptz not null,
  generation   int not null default 1, -- номер прогона, см. §5.7
  created_at   timestamptz not null default now()
);

poll_options (
  id        uuid primary key,
  poll_id   uuid not null references polls(id) on delete cascade,
  text      text not null,
  position  int not null,
  unique (poll_id, position)
);

poll_results (                          -- агрегаты, снапшот из Redis
  poll_id     uuid not null references polls(id) on delete cascade,
  option_id   uuid not null references poll_options(id) on delete cascade,
  votes       bigint not null,
  generation  int not null,
  updated_at  timestamptz not null default now(),
  primary key (poll_id, option_id)
);

poll_totals (                           -- число проголосовавших, см. §5.8
  poll_id     uuid primary key references polls(id) on delete cascade,
  voters      bigint not null,
  generation  int not null,
  updated_at  timestamptz not null default now()
);
```

Тип `a/b` отдельной сущностью не является — это `single` с двумя вариантами.

**Сырые голоса не хранятся нигде.** Ни таблицы, ни лога, ни очереди с индивидуальными
событиями. Обезличенность из ТЗ обеспечена структурно, а не политикой доступа: связать
голос с человеком невозможно, потому что такой записи не существует. Побочно это снимает
вопросы хранения персональных данных.

### Redis

```
dedup:{poll_id}:{token}        SET NX EX <ttl>   единственная синхронная операция
poll:{poll_id}:counts:{shard}  HASH option_id → int64, HINCRBY
poll:{poll_id}:voters:{shard}  INCR
```

`shard` — порядковый номер инстанса по модулю `N` (по умолчанию 4). Ординал, а не
`hash(instance_id)`: хеш без нужды схлопнул бы два инстанса в один шард. Читатель
суммирует `N` хешей.

Шардирование счётчиков не решает существующей проблемы (§2), но схему ключей нельзя
менять под нагрузкой, а лишний `HGETALL` раз в секунду не стоит обсуждения.

```json
→ {"option_ids": ["..."]}
← 200 {"accepted": true}
```

| Код | Причина |
|---|---|
| `200` | голос принят |
| `400` | невалидные `option_ids` (несуществующие, дубли, нарушен `max_choices`) |
| `409` | по этому токену уже голосовали |
| `410` | опрос закрыт (`now() > ends_at + grace`) |
| `425` | опрос ещё не начался |
| `429` | превышен лимит частоты (отдаёт nginx) |

| Метод | Путь | Описание |
|---|---|---|

## 9. Принятые компромиссы

Перечислены явно, потому что каждый — осознанный выбор, а не недоделка.

| Компромисс | Цена | Почему приемлемо |
|---|---|---|
| Дедуп обходится очисткой cookie | накрутка технически подкованным пользователем | прямое требование ТЗ; строгая идентификация несовместима с анонимностью |
| fail-open при отказе Redis | во время инцидента дедупа нет | результат опроса ценнее, чем защита от накрутки |
| Потеря батча при жёстком отказе инстанса | ~1600 голосов из 10 млн (0,016%) | статистически незначимо; при плановом рестарте — ноль |
| Eventual consistency агрегатов | админка отстаёт на секунды | точность до единицы в реальном времени никому не нужна |
| Rate limit per-node, не глобальный | фактический порог выше номинального в K раз | лимит и так приблизительный; экономит дефицитный ресурс |
| Grace period +2-3 с | принимаются голоса после формального дедлайна | иначе теряется хвост легитимных голосов у зрителей с плохой связью |
| Сырые голоса не хранятся | невозможен пересчёт и аудит по событиям | обезличенность из ТЗ; аудит — пункт roadmap |

## 10. Roadmap

Не реализовано в рамках задания, но продумано.

**Локальный дедуп через маршрутизацию по хешу токена — снимает последний RTT.**
Если nginx маршрутизирует по `hash $cookie_vote_token consistent`, все запросы с одним
токеном попадают на один инстанс, и дедуп становится in-memory мапой: **ноль обращений к
Redis на горячем пути**, Redis остаётся только под счётчики. Это устраняет узкое место,
определённое в §2.

Это не sticky sessions: маршрутизация детерминирована от значения ключа, состояние не
сессионное, а шардированное. Плата — рестарт инстанса теряет его долю дедуп-состояния
(эквивалентно уже принятому fail-open), изменение числа инстансов перетасовывает часть
токенов. Для 60-секундного окна, где инстансы всё равно не масштабируются на лету, обе
платы близки к нулю.

Обязательная деталь: при отсутствии куки `hash` считается от пустой строки, и **все**
запросы без токена летят на один инстанс. Первый заход зрителя — как раз без куки. Поэтому
минт-путь маршрутизируется отдельно (round-robin), а хеш применяется только к `/vote`, где
токен гарантированно есть. Память под локальный дедуп: 10 млн токенов на 24 инстанса —
порядка 400 тыс. записей на инстанс, десятки мегабайт с TTL-вытеснением.

**Минт токена на edge compute.** Cloudflare Worker или nginx njs с ключом подписи: origin
перестаёт видеть ~20 млн запросов на минт вообще.

**Redis Cluster.** Нужен уже при явке выше расчётной: дедуп упирается первым. Ключи
шардируются сами, требуется только добавление нод.

**Персистентность сырых событий (Kafka).** Если появится требование аудита или пересчёта
— поток событий в лог, агрегация отдельным консьюмером. Прямо противоречит текущему
решению не хранить сырые голоса, поэтому требует явного продуктового решения о
персональных данных.

**Автоскейлинг по расписанию эфира.** Реактивный по метрикам бесполезен (§1); мощность
поднимается до начала ролика и снимается после.
