# vote-sys

Сервис анонимных голосований под нагрузку ТВ-эфира: ~100 млн зрителей, окно ~60 секунд.

- **[architecture.md](./architecture.md)** — обоснование архитектуры и технологий, нагрузочный расчёт
- [plan.md](./plan.md) — план реализации с критериями приёмки
- [ai/](./ai/) — артефакты работы с ИИ: лог проектирования и реестр ошибок
- [task.md](./task.md) — исходное ТЗ

---

## Что делает сервис

| Возможность | Где |
|---|---|
| Анонимно проголосовать | `POST /api/polls/{id}/vote` + лендинг `/p/{id}` |
| Создать опрос | `POST /api/admin/polls` + админка `/admin` |
| Посмотреть обезличенные результаты | `GET /api/admin/polls/{id}/results` |

Типы вопросов: `single` (в том числе a/b) и `multiple` с ограничением `max_choices`.

**Сырые голоса не хранятся нигде** — ни таблицы, ни лога, ни очереди событий.
Обезличенность обеспечена структурно, а не политикой доступа: связать голос с
человеком невозможно, потому что такой записи не существует.

## Запуск

Нужен только Docker. Go нужен, если хочется гонять тесты и нагрузку с хоста.

```sh
cp .env.example .env
make up        # nginx + 3 инстанса + Redis + Postgres
```

Стенд поднимает три инстанса за nginx, а не один, чтобы дедуп, шардирование
счётчиков и идемпотентный upsert проверялись в тех же условиях, в которых
работают в проде.

Проверка, что всё живо:

```sh
curl -sf localhost:8080/healthz     # {"shard":0,"status":"ok"}
```

`/healthz` — это readiness, а не liveness: 200 появляется только после прогрева
пулов и загрузки метаданных активных опросов.

### Первый опрос

```sh
make seed                            # печатает id созданного опроса
open http://localhost:8080/admin     # админка, токен из ADMIN_BEARER_TOKEN
open http://localhost:8080/p/<id>    # страница зрителя
```

`make help` — остальные цели.

## Как потрогать руками

```sh
POLL=$(make seed 2>/dev/null | tail -1)
OPT=$(curl -s localhost:8080/api/polls/$POLL | jq -r '.options[0].id')

# 1. Токен: минт ставит куку. Именно POST, и это принципиально — см. §5.1
curl -sc jar -X POST localhost:8080/api/token \
  -H 'Content-Type: application/json' -d "{\"poll_id\":\"$POLL\"}"

# 2. Голос
curl -sb jar -X POST localhost:8080/api/polls/$POLL/vote \
  -H 'Content-Type: application/json' -d "{\"option_ids\":[\"$OPT\"]}"
# {"accepted":true}

# 3. Повтор той же кукой
curl -sb jar -X POST localhost:8080/api/polls/$POLL/vote \
  -H 'Content-Type: application/json' -d "{\"option_ids\":[\"$OPT\"]}"
# {"code":"already_voted",...}   409

# 4. Результаты для оператора — видны во время голосования
curl -s -H "Authorization: Bearer dev-admin-token" \
  localhost:8080/api/admin/polls/$POLL/results | jq

# 5. Публичные результаты — только после закрытия
curl -si localhost:8080/api/polls/$POLL/results | head -3
# HTTP/1.1 425 Too Early
```

### Что стоит проверить отдельно

**Лендинг не ставит куку.** Если бы токен выдавался заголовком на кэшируемой
странице, один закэшированный ответ раздал бы **один токен всем зрителям**, и
первый же `SET NX` заблокировал бы остальных. Это худший сценарий из возможных,
поэтому проверка смотрит только заголовки:

```sh
curl -s -D - -o /dev/null localhost:8080/p/$POLL | grep -ci '^set-cookie'   # 0
```

**Клиентский таймер не зависит от часов устройства.** Переведите часы браузера на
5 минут вперёд и откройте `/p/{id}`: кнопка не должна погаснуть досрочно. Отсчёт
идёт от `server_time` из ответа, а не от `Date.now()` — на потребительских
телефонах часы врут на минуты.

## Тесты

```sh
make test        # go test ./... -race
make lint        # go vet
```

Восемь пакетов, всё под `-race`. Что покрыто помимо очевидного:

| Проверка | Почему она есть |
|---|---|
| `Swap` под гонкой 64 горутин × 2000 инкрементов | сумма дельт плюс остаток обязана сойтись точно |
| Нулевые аллокации в `Add`, `ValidateChoice`, `Lookup`, `Allow` | горячий путь, 20 нс на голос |
| Размер счётчика равен кэш-линии | без паддинга ядра гоняли бы одну строку между собой |
| Разомкнутая цепь не делает обращений к Redis **вовсе** | иначе breaker не защищает от деградации |
| Дедлайн соблюдается, когда хранилище игнорирует контекст | регрессия на реальный отказ, см. ниже |
| Неоднозначный сброс не повторяется | `HINCRBY` не идемпотентен: повтор задваивает |
| Форма ключей Redis | опечатка в ней не ломает ни сборку, ни тесты логики |
| Адрес зрителя не попадает в лог | пара «IP + poll_id + время» воссоздала бы запись, которой нет в базе |

## Нагрузочный тест

```sh
make load                       # профиль ТВ, 500 RPS среднее, 60 с
RPS=1000 DURATION=90s make load
```

Генератор воспроизводит профиль эфира, а не ровный поток: ровная нагрузка не
проверяет главное — поведение под импульсом, а именно им определена вся
архитектура.

Профиль выведен, а не подобран. Условие «половина голосов приходится на первую
треть окна» сводится к `u² + u − 1 = 0`, где `u = e^(−D/3τ)`; корень равен
обратному золотому сечению, отсюда `τ = D/1,4436`, а пик выше среднего в 1,89
раза. Моменты отправки берутся обратной функцией распределения по равномерным
квантилям — профиль получается гладким и воспроизводимым, поэтому прогоны
сравнимы между собой.

### Результаты

Стенд: AMD Ryzen 7 5700U (16 потоков), 13 ГБ, всё в одном Docker на одном хосте.
Сырые данные — [bench/load-baseline.csv](./bench/load-baseline.csv).

**Базовый прогон** — 30 000 голосов за 60 с, пик 925 RPS:

| Метрика | Значение |
|---|---|
| p50 | 2,05 мс |
| p95 | 3,39 мс |
| p99 | 96,6 мс |
| Коды ответа | 100% `200` |
| Сходимость | принято 30000 = участников 30000 = сумма голосов 30000 |

p99 держат первые полсекунды прогона — установка соединений. В первой секунде
средняя 74 мс, со второй и дальше — около 2 мс.

**Жёсткое убийство инстанса** (`SIGKILL` на 32-й секунде):

| Метрика | Значение |
|---|---|
| Потеряно | 4 голоса из 29994 — **0,013%** |
| Расчёт §5.4 предсказывал | 0,016% |
| Инвариант `single` | держится |

**Отказ Redis** (остановлен на 25-й секунде, возвращён на 45-й):

| Метрика | Значение |
|---|---|
| Принято | все 30 000, ни одного 5xx |
| Латентность во время отказа | **упала** до 1,5–1,7 мс |

Латентность падает потому, что разомкнутая цепь убирает единственный синхронный
round-trip на горячем пути. Fail-open работает буквально так, как описан в §6:
дедуп отключается, голоса продолжают считаться.

### Чего этот прогон НЕ доказывает

**Ёмкость.** Пик 925 RPS при p50 в 2 мс означает, что система простаивала: мы
замерили латентность на холостом ходу, а не нашли точку отказа. Генератор делит
16 потоков с сервисом, поэтому цифра относится к паре «генератор + сервис».
Топология сведена в один хост — узкое место из §2 (дедуп, которому при 250K
ops/sec нужны 3-6 нод Redis) на такой конфигурации проявиться не может.

**Расчётные 250K RPS из §2 остаются расчётом, а не измерением.** Чтобы измерить
ёмкость, нужен генератор на отдельных машинах, ступенчатое наращивание до отказа
и разнесённые Redis с Postgres.

Прогон доказывает другое, и это тоже ценно: корректность деградаций, совпадение
потерь с расчётом, работу fail-open и точную сходимость счётчиков.

### Сценарии отказов вручную

Запустить нагрузку в одном терминале, а во втором — вмешаться:

```sh
# терминал 1
make load

# терминал 2, на середине прогона
docker kill vote-sys-api2-1        # жёсткий отказ инстанса
docker compose stop redis          # отказ дедупа; вернуть: docker compose start redis
```

После отказа Redis он поднимется пустым — персистентности у него нет намеренно.
Это и есть сценарий «потеря Redis в середине опроса» из §5.7: агрегаты в Postgres
защищены `GREATEST`, а вернуть счётчики к меньшему значению можно только через
`make reset`, который поднимает `generation`.

## Принятые компромиссы

Каждый — осознанный выбор, а не недоделка. Подробности в
[architecture.md §9](./architecture.md).

| Компромисс | Цена | Почему приемлемо |
|---|---|---|
| Дедуп обходится очисткой cookie | накрутка технически подкованным пользователем | прямое требование ТЗ; строгая идентификация несовместима с анонимностью |
| fail-open при отказе Redis | во время инцидента дедупа нет | результат опроса ценнее защиты от накрутки |
| Потеря батча при жёстком отказе инстанса | 0,013% (измерено) | при плановом рестарте — ноль |
| Eventual consistency агрегатов | админка отстаёт на секунды | точность до единицы в реальном времени не нужна |
| Rate limit per-node, не глобальный | фактический порог выше номинального | лимит и так приблизительный, а Redis — дефицитный ресурс |
| Grace period +3 с | принимаются голоса после формального дедлайна | иначе теряется хвост у зрителей с плохой связью |
| Сырые голоса не хранятся | невозможен пересчёт и аудит по событиям | обезличенность из ТЗ; аудит — пункт roadmap |
| Промежуточные результаты скрыты | зритель не видит счёт до конца | bandwagon effect обесценил бы опрос методологически |

## Что показал этот проект про работу с ИИ

Подробный разбор — в [ai/corrections.md](./ai/corrections.md), там 25 ошибок с
указанием, кто нашёл каждую. Три вывода стоят того, чтобы вынести их сюда.

**Три ошибки жили в документе, а не в коде.** Порог батча, гарантия таймаута и
escape hatch генерации выглядели убедительно в архитектурном тексте и оказались
неверны при попытке их реализовать. Никакое количество раундов разбора их бы не
поймало — проектирование без реализации их пропустило.

**Одну ошибку не нашла ни одна автоматическая проверка.** Дедуп обходился
перезагрузкой страницы: лендинг запрашивал токен при каждой загрузке, и новый
затирал куку. Все тесты работали с одним токеном на сценарий и повторную загрузку
не воспроизводили. Нашлась она только ручным проходом по продукту в браузере.

**Оснастка врала чаще проверяемого кода.** Шесть ложных срабатываний за проект —
и ни одного случая, когда виноват оказался код раньше, чем соврала проверка.
Отсюда правило, выведенное на ходу: если результат выглядит неожиданно,
сомневаться сперва в измерении.

## Что не сделано

Осознанно оставлено за рамками, обосновано в [architecture.md §10](./architecture.md):

- **Локальный дедуп через маршрутизацию по хешу токена** — снимает единственный
  синхронный round-trip и вместе с ним потолок системы.
- **Минт токена на edge compute** — убирает с origin ~20 млн запросов.
- **Redis Cluster** — нужен уже при явке выше расчётной.
- **Персистентность сырых событий** — потребует явного решения о персональных
  данных, потому что прямо противоречит текущему выбору не хранить голоса.
- **Автоскейлинг по расписанию эфира** — реактивный по метрикам бесполезен: за 60
  секунд он не успевает.
