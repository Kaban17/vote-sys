# Артефакты работы с ИИ

ТЗ требует, чтобы все артефакты работы с ИИ лежали в репозитории и не
скрывались. Здесь они в исходном виде, без приглаживания.

## Состав

| Файл | Что это |
|---|---|
| [`transcript-design.md`](./transcript-design.md) | лог обсуждения архитектуры: исходные предложения, критика, отвергнутые варианты |
| [`corrections.md`](./corrections.md) | реестр ошибок — что было предложено неверно, кто заметил, чем закончилось |

В `transcript-design.md` есть помеченный пропуск: фрагмент обсуждения между
разбором ТЗ и сводкой не сохранился, контекст был свёрнут. Восстанавливать те
реплики по памяти не стали — это была бы подделка артефакта, а не артефакт.

## Как использовался ИИ

Обсуждение архитектуры велось в формате разбора: предложение → критика →
исправление. Значительная часть решений в `architecture.md` появилась именно как
результат найденных ошибок, а не как первая версия.

Наиболее важные исправления, дошедшие до финального дизайна:

1. **Дедупликация по IP отброшена.** Первоначальная схема «cookie + hash(IP)» при
   CGNAT вырезала бы легитимное большинство мобильных зрителей. IP оставлен
   только как rate limit.

2. **Приоритеты по нагрузке инвертированы.** Изначально узким местом считались
   счётчики (страх hot key). После расчёта выяснилось, что после батчинга на них
   приходится ~1000 ops/sec, а реальный потолок — дедуп с его 250K синхронных
   round-trip'ов.

3. **Set-Cookie на кэшируемом лендинге.** Самая опасная из найденных ошибок: один
   закэшированный ответ раздал бы всем зрителям один и тот же токен и уничтожил
   бы опрос целиком. Решено структурно — отдельным POST-эндпоинтом, который не
   кэшируется по спецификации HTTP, а не по настройке.

4. **Circuit breaker вместо одного таймаута.** Таймаут ограничивает урон от
   одного запроса, но при деградации Redis каждый из 250K запросов честно ждёт
   свои 50 мс и выедает пул.

5. **Счётчик участников отдельно от суммы голосов.** При `kind = multiple`
   проценты от `sum(votes)` дали бы больше 100%.

Подробности каждого пункта — в [`corrections.md`](./corrections.md) и в
соответствующих разделах `architecture.md`.

Отдельно стоит отметить раскол по фазам. В проектировании почти все ошибки нашёл
человек, разбирая предложенное моделью. В реализации — наоборот, и все они
всплыли **запуском, а не чтением кода**: он компилировался, тесты проходили,
`go vet` молчал. Отсюда решение писать критерии приёмки в `plan.md` как команды с
ожидаемым результатом, а не как «реализован пакет X».
