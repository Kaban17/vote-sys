# План реализации

Архитектура и обоснования — [architecture.md](./architecture.md). Здесь только
порядок работ, критерии готовности и то, чем жертвовать при нехватке времени.

**Бюджет:** 48 часов календарно, ~22 часа работы. Оценки ниже в часах работы.

---

## Принципы порядка

Шаги — вертикальные срезы, а не слои. Каждый заканчивается чем-то, что можно
запустить и проверить командой, а не «реализован пакет X».

Две зависимости жёсткие и определяют весь порядок:

- **Голос считается (4) до дедупа (5).** Дедуп поверх неработающего счёта
  неотлаживаем: непонятно, голос не долетел или его отсекли.
- **Результаты (6) до нагрузочного теста (8).** Тест проверяет сходимость
  агрегатов; без агрегатов мерить нечего, кроме RPS, а RPS сам по себе ничего
  не доказывает.

Остальное можно переставлять.

## Шаг 1. Каркас запуска — 2 ч

**Цель:** стенд поднимается, трафик проходит через nginx до Go-инстанса.

**Делаем:** `internal/config`, `internal/platform/{postgres,redis,shutdown}.go`,
`cmd/api/main.go`, `handleHealth`.

Пулы создаются и прогреваются на старте (`MinConns = MaxConns`, `Ping`), а не
лениво по первому запросу — architecture.md §6. `/healthz` отдаёт `ready` только
после прогрева.

**Критерий приёмки:**

```sh
make up
curl -sf localhost:8080/healthz          # 200 от всех трёх инстансов
docker compose logs api1 | grep -i panic # пусто
```

**Не делаем:** ничего доменного.

---

## Шаг 2. Домен и Postgres — 2,5 ч

**Цель:** опрос можно создать и прочитать.

**Делаем:** `internal/poll/{model,store}.go`, `internal/httpapi/{admin,errors}.go`,
`requireAdmin`, `scripts/seed.sh`.

`ValidateChoice`, `StateAt`, `AcceptsVoteAt`, `IndexOf` — с юнит-тестами. Это
чистые функции без зависимостей, и покрыть их дёшево; они же несут краевые случаи
(grace period, `max_choices`, дубли в `option_ids`).

**Критерий приёмки:**

```sh
make migrate && make seed
curl -H "Authorization: Bearer $ADMIN_BEARER_TOKEN" localhost:8080/api/admin/polls
go test ./internal/poll/ -race
```

Опрос виден в списке; тесты на `AcceptsVoteAt` покрывают до/во время/после/в grace.

**Не делаем:** результаты — их пока нет.

---

## Шаг 3. Токен — 1 ч

**Цель:** анонимная идентичность выдаётся и проверяется.

**Делаем:** `internal/token/hmac.go`, `internal/httpapi/token.go`.

`hmac.Equal` для сравнения. Токен привязан к `poll_id`: токеном от одного опроса
нельзя проголосовать в другом.

**Критерий приёмки:**

```sh
curl -si -X POST localhost:8080/api/token -d '{"poll_id":"..."}' | grep -i set-cookie
go test ./internal/token/ -race
```

Тесты: валидный токен проходит; подделанная подпись, чужой `poll_id` и
просроченный токен — нет.

**Проверить отдельно:** ответ минта несёт `Cache-Control: no-store`, а лендинг
`/p/{id}` — **не** несёт `Set-Cookie`. Это та ошибка, которая уничтожает опрос
целиком (architecture.md §5.1), и проверять её надо руками, а не надеяться на
ревью.

---

## Шаг 4. Голос считается — 3 ч

**Цель:** голос долетает до Redis, суммы сходятся.

**Делаем:** `internal/vote/{counter,batcher}.go`, `internal/poll/cache.go`,
`internal/httpapi/{vote,poll}.go` (кроме дедупа).

Порядок проверок в хендлере — сразу правильный (410 → 400 → … ), даже без шага 5
на своём месте.

**Критерий приёмки:**

```sh
go test ./internal/vote/ -race          # включая конкурентный тест Add/Swap
# 1000 голосов → HGETALL по всем шардам даёт ровно 1000
```

Обязательные тесты:

- `Swap` под гонкой не теряет и не задваивает инкременты (`-race`, N горутин);
- `Restore` после неудачного flush возвращает значения — без него они теряются
  при полностью живом инстансе (architecture.md §5.6);
- финальный flush при отмене контекста.

**Не делаем:** дедуп. Голосовать можно сколько угодно — это ожидаемо на этом шаге.

---

## Шаг 5. Дедуп и fail-open — 2,5 ч

**Цель:** повтор отсекается, а отказ Redis не роняет приём.

**Делаем:** `internal/dedup/redis.go`, `internal/breaker/breaker.go`, подключение
в `handleVote`.

**Критерий приёмки:**

```sh
# повторный голос с той же кукой
curl ... /vote   # 200
curl ... /vote   # 409

# fail-open: приём продолжается без Redis
docker compose stop redis
curl ... /vote   # 200, не 503
docker compose start redis
```

Тесты breaker'а: размыкание после N ошибок в окне, probe в half-open, возврат в
closed. Важно проверить, что в разомкнутом состоянии обращения к Redis **не
происходит вовсе** — иначе breaker бесполезен против деградации (architecture.md §6).

---

## Шаг 6. Результаты — 3 ч

**Цель:** агрегаты доезжают до Postgres и видны в админке.

**Делаем:** `internal/results/{snapshotter,persister}.go`, `handleAdminResults`,
`handlePublicResults`.

**Критерий приёмки:**

```sh
# инвариант: для kind=single число участников равно сумме голосов
# держится и в Redis, и в Postgres
psql -c "SELECT voters, (SELECT sum(votes) FROM poll_results WHERE poll_id=...) FROM poll_totals WHERE poll_id=..."

# публичные результаты молчат до закрытия
curl -si /api/polls/{id}/results   # 425 пока идёт, 200 после ends_at

# generation переживает сброс
make reset && # цифры обнуляются, а не замораживаются на старых
```

Инвариант `single: voters == sum(votes)` — самый дешёвый тест во всём проекте:
он бесплатно ловит ошибки батчера, шардирования и upsert'а сразу.

Проверить `X-Cache-Status: HIT` на повторном запросе результатов после закрытия —
иначе two-phase кэширование не работает и весь read path остаётся на origin.

## Шаг 7. Фронт — 2,5 ч

**Цель:** зритель может проголосовать со страницы, оператор — создать опрос.

**Делаем:** `web/index.html`, `web/admin.html`.

Таймер на лендинге считается по offset между `server_time` и `Date.now()`, а не
по часам устройства (architecture.md §5.5). Проверяется переводом системных часов
браузера на 5 минут вперёд — кнопка не должна погаснуть досрочно.

Админка показывает проценты от `voters`, а не от суммы, и выводит `stale_for_ms`.

**Критерий приёмки:** полный путь руками — создать опрос в админке, открыть
лендинг, проголосовать, увидеть цифры в админке, дождаться `ends_at`, увидеть
публичные результаты.

**Режется первым при нехватке времени** — ТЗ называет фронт опциональным.

---

## Шаг 8. Нагрузочный тест — 3 ч

**Цель:** цифры для README и подтверждение, что деградации работают как описано.

**Делаем:** `cmd/loadgen`.

Профиль ТВ (~50% голосов в первые 20 с), не ровный поток: ровная нагрузка не
проверяет главное — поведение под импульсом.

**Сценарии:**

| Сценарий | Что доказывает |
|---|---|
| Базовый прогон | RPS, p50/p95/p99, доля 409/429 |
| Убить инстанс на середине | потеря ≈ `FLUSH_INTERVAL × RPS/N`, остальные не затронуты |
| Остановить Redis на середине | fail-open: приём продолжается, дедуп временно отключён |
| Сходимость | принято голосов == агрегат в Postgres после закрытия (с точностью до потерь) |

**Критерий приёмки:** график и таблица в README с реальными числами и указанием
железа. Числа со стенда на ноутбуке — не доказательство 250K RPS, и об этом надо
написать прямо: тест проверяет корректность деградаций и порядок величин, а не
продовую ёмкость.

**Режется до одного базового прогона + сценария с Redis** при нехватке времени.

## Шаг 9. README и AI-артефакты — 2 ч, не режется

**Цель:** выполнить пункты 1 и 3 ТЗ.

**Делаем:**

- README: описание сервиса, запуск, тестирование, результаты нагрузочного теста,
  явная таблица компромиссов.
- `ai/transcript-design.md` — **полная выгрузка диалога проектирования**, без
  приглаживания. Сейчас её нет, и это единственный незакрытый пункт ТЗ.
- `ai/corrections.md` — найденные в ходе обсуждения ошибки и их судьба.

ТЗ требует артефакты, а не пересказ. Ценность здесь именно в неприглаженности:
отброшенные варианты и исправленные ошибки показывают ход рассуждения лучше, чем
финальный документ.

## Риски

**Выгрузка диалога окажется объёмнее ожидаемого.** Вероятно, часа не хватит.
Начать её раньше, не откладывая на шаг 9 целиком.

**Нагрузочный тест упрётся в клиент, а не в сервер.** Генератор на том же
ноутбуке конкурирует с сервисом за ядра. Мерить не абсолютный RPS, а поведение:
доли кодов ответа, сходимость, форму латентности. Абсолютные числа честно
пометить как «на таком-то железе, клиент и сервер на одной машине».

**Тесты на конкурентность дадут ложное зелёное.** `-race` ловит гонки только на
исполненных путях. Для `Swap`/`Restore` нужен тест с большим числом горутин и
проверкой точной суммы, а не просто отсутствие паники.
